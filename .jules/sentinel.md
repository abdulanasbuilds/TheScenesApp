# Sentinel Security Journal

## 2025-08-04 - Timing Attack Risk and Permissive Bypass in Webhook Signature Verification
**Vulnerability:** Webhook signature verification in `src/lib/payment-adapter.ts` compared the computed HMAC-SHA512 hash with the header-provided signature using standard string equality (`===`), exposing the system to potential timing attacks. Additionally, if the webhook secret `PAYSTACK_WEBHOOK_SECRET` was unconfigured, it bypassed verification entirely with a warning, posing a significant risk if misconfigured in production.
**Learning:** Critical webhook endpoints must always fail securely in production even if configuration is missing. Moreover, signature verification should use a constant-time comparison helper to mitigate side-channel timing attacks.
**Prevention:** 1. Implement a robust, runtime-agnostic constant-time string comparison function (`safeCompare`). 2. Explicitly verify that webhook signature validation is never bypassed in production environments by checking `process.env.NODE_ENV === 'production'`.

## 2026-08-05 - Balance Desync and Concurrency Race Conditions in Withdrawal Processing
**Vulnerability:** Creators were able to bypass withdrawal limits and request duplicate payouts beyond their ledger balance. This occurred because `createWithdrawalRequest` checked balance against raw ledger entries without subtracting pending requests (causing a fee phantom-balance desync), and `processWithdrawal`/`markWithdrawalFailed` lacked atomic status checks, making them vulnerable to race conditions where the database state was fetched first and updated second, potentially leading to double-deductions or double-crediting.
**Learning:** Checking balances on ledger-based systems must account for in-flight/pending requests' gross amounts (including fees) before committing. Additionally, state transition updates must execute atomically on the expected original state to prevent concurrency-based double operations.
**Prevention:** Always filter updates by the expected original state (`status = 'pending'` or `status = 'processing'`) when committing sensitive state transitions. Verify that the query modified exactly one row before executing side effects (like adding ledger entries or triggering payout transfers).
