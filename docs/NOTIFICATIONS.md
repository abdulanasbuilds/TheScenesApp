# Connected in-app notifications (P4-S3)

**Status:** P4-S3 implemented as code/local work (ADR-044, 11 November 2026). Remote actions: **NONE**.
The migration is authored and locally reviewed; it is **not** applied to any hosted project. No
push/email provider is connected.

This document is the operator and reviewer reference for the notification tables, the client/server
surface and the event/preference matrix.

## What it does

- `/notifications` is authenticated, newest-first and keyset-paginated. Default page size 20, maximum 50. The page has loading, empty, all/unread filter, retry and unavailable states.
- "Mark read" and "mark all read" are awaited, caller-bound server functions. Controls are disabled
  while a request is pending, so a double click cannot submit twice.
- The shell unread badge comes from the connected unread count (root-loader summary), not from fixture
  data.
- Settings → Notifications shows the connected channel/category preferences and saves them to the
  caller's own row.
- Fixture mode is unchanged: the fixture notifications page and local switches behave exactly as
  before.

## Data model

Migration: `supabase/migrations/20261111120000_phase4_0019_notifications.sql` (additive).

### `public.notifications`

- `id uuid` primary key, `user_id uuid not null references auth.users(id) on delete cascade`;
- `type text` in `community_joined | course_enrolled | lesson_completed | system`;
- `title text` (1–120), `body text` (1–500);
- `href text null` constrained to the internal allowlist below;
- `dedupe_key text` (1–160); unique `(user_id, dedupe_key)`;
- `read_at timestamptz null`, `created_at timestamptz not null default now()`;
- keyset index `(user_id, created_at desc, id desc)` and a partial unread index.

Access: RLS enabled; `anon` has nothing; `authenticated` has `select` on the read columns and `update`
on **only** `read_at`. There is no client insert/delete. Both policies are owner-only
(`user_id = (select auth.uid())`).

### `public.notification_preferences`

- `user_id uuid` primary key → `auth.users`;
- explicit boolean columns: `in_app_learning`, `in_app_community`, `in_app_product`,
  `email_learning`, `email_community`, `email_product`, `push_learning`, `push_community`,
  `push_product`;
- `created_at`, `updated_at` maintained by the shared timestamp trigger.

Access: RLS enabled; owner-only `select`/`insert`/`update` with column grants. `updated_at` is not
client-writable. There is **no** column that can suppress account/security notices: those are mandatory
in-app and are not representable in the preference row.

## Event matrix

Notifications are generated by one `after insert` trigger on `private.audit_events`
(`private.create_notification_from_audit_event`), so the notification is written **atomically** in the
same transaction as the caller-bound transition. Recipient = the audit actor. The dedupe key is
`'audit:' || event.id`, and the insert uses `on conflict (user_id, dedupe_key) do nothing`, so a
replayed event produces exactly one notification.

| Audit action       | Notification type  | Default | Emitted now                                    |
| ------------------ | ------------------ | ------- | ---------------------------------------------- |
| `community.joined` | `community_joined` | on      | yes                                            |
| `course.enrolled`  | `course_enrolled`  | on      | yes                                            |
| `lesson.completed` | `lesson_completed` | off     | no (noisy)                                     |
| — (`system`)       | `system`           | —       | reserved for a privileged, audited server path |

Comments, mentions, new creator content and event reminders stay fixture-labelled/deferred until the
owning Phase 5 data exists.

The trigger consults the recipient's in-app preference for the category and treats an absent row as the
safe default (on).

## `href` allowlist

Notification links can only be one of these internal relative paths (enforced by the database check
**and** the client zod schema, so data cannot create an open redirect):

```text
/home
/my-learning
/notifications
/settings
/c/<community-slug>
/c/<community-slug>/classroom/<course-slug>
```

## API surface

Client functions (`src/features/notifications/notifications.functions.ts`):

- `getNotificationsPage({ filter, cursor, limit })` — `GET`; returns `{ items, nextCursor, unreadCount }`;
- `getNotificationUnreadCount()` — `GET`; root-loader summary, returns `{ unreadCount }` (0 when signed
  out, never an error);
- `markNotificationRead({ id })`, `markAllNotificationsRead()` — `POST`;
- `getNotificationPreferences()`, `updateNotificationPreferences(preferences)`.

The keyset cursor is `"<createdAt>|<uuid>"` and is validated and decoded in the input schema, so a
tampered cursor becomes a normal field validation error, never a malformed query.

## Failure behaviour

- Reads/writes are caller-bound through the request Supabase client; RLS is the real boundary.
- A not-signed-in caller gets `UNAUTHENTICATED` and is sent to `/login`.
- An unexpected provider failure is presented as a safe, retryable `UNAVAILABLE` state with no provider
  detail.
- The root-loader summary never throws: a signed-out visitor or a transient failure yields an unread
  count of 0 so the shell still renders.

## Rollback

The migration is additive. Drop the `audit_events_create_notification` trigger, the
`private.create_notification_from_audit_event()` function, and the two tables; revert
`src/features/notifications/`, `src/server/{repositories,services}/notification.*.server.ts`, the
`notifications.tsx` route, the settings notifications tab, and the root-loader/store summary wiring. No
hosted state exists to undo.
